# Implementation and Research Workflow

Write this skill and its references, along with Task/Report files, in English by default. Keep all user-facing dialogue and Q&A in Japanese.

必要な工程から始める。調査のみの依頼では、コード編集の工程へ自動で進まない。
書式は `Docs/CodingStandard.md`、設計の参照先と作業上の制約はリポジトリの `AGENTS.md` に従う。
機械処理は Skill の scripts にある補助スクリプトを使う。

## モデルと役割

- 上位モデル: 設計資料の読解、責務・API 契約の判断、ユーザーへの Q&A、作業分担、検証方針、最終レビューを担当する。
- 下位モデル: コード調査と情報の抽出・整理、指示された契約に沿ったヘッダー・Doxygen・テスト・実装の編集、指定された検証、質問・結果の報告を担当する。
- Skill 内の [settings.jsonc](../settings.jsonc) で役割ごとの選択方法、候補 sequence、固定モデル map を指定する。今回のユーザーの明示指定を優先する。
- 固定指定では model／effort をそのまま使う。選択を委譲された場合は、上位モデルが候補から作業に適した組み合わせを選び、Task に記録する。
- 候補の順序は選択時の優先順であり、先頭を機械的に採用しない。未設定や利用不能の場合は必要な設定を確認し、別の値へ黙って置き換えない。
- セッション中の明示指定と承認を引き継ぎ、同じ設定を再確認しない。
- 実際の上位モデルと設定が異なる場合は、その差分を伝えて確認する。Skill が現在のチャットのモデルを切り替えられるとは扱わない。
- 下位モデルの起動時に指定を渡す。実際の設定を確認できない場合は、指定モデルを使用したと断定しない。

設定形式と機械処理の詳細は [AutomationPlan](AutomationPlan.md) を必要な工程で読む。

## 委任中の動き

上位モデルは委任後、原則として通知を待って Idle にする。独立して必要な作業がある場合だけ進める。
子と同じ調査、作業中のコードの逐次レビュー、進捗確認のための頻繁なファイル読み取りや催促をしない。
完了時または判断依頼時に Report と必要な差分を確認する。修正指示は関連事項をまとめ、必要な確認が通ったら終える。
下位モデルは [WorkerGuide](WorkerGuide.md) に従い、通常の判断を自律的に行う。小さな進捗通知を必須にしない。

## 受け渡し

1. Session は開始時に一度、Run は新しい作業依頼の開始時に一度だけ作成する。Task の追加では既存の SessionId／RunId を再利用する。
2. `.codex/working/_Template/Task.md` と `Report.md` をコピーし、`.codex/working/session-<SessionId>/run-<RunId>/Task-<TaskId>/` に `Task.md` と `Report.md` を作る。TaskId は Task 作成時だけ発行する。
3. Task は上位モデル、Report は担当する下位モデルだけが更新する。sessionId／runId／taskId を一致させる。
4. Task に今回の工程・対象ファイル・確定した契約・制約・資料の参照先・必要な検証・完了条件をまとめる。
5. Report に未確定事項と提案、変更、検証の終了コード・件数・ログパス、残作業をまとめる。

Markdown 先頭の JSON ブロックを機械処理用メタデータとし、本文を短い指示・根拠・結果の記録にする。
連絡が必要な場合は、短い質問・回答・完了通知を message で伝えてよい。Report は判断待ち・完了・再開に必要な状態変更で更新し、逐次報告を目的にしない。
チャット履歴全体の共有を必須にせず、担当 Task と必要な資料を渡す。担当外の Task／Report は読まない。
長いログやソースを受け渡しファイルへ転載せず、必要な結果と参照先を書く。
同一作業ではファイルを使い続け、現在の指示・未回答の質問・最新の結果を中心に保つ。
session は継続する作業セッション、run は一回の依頼、Task は分担した作業を表す。途中再開で新しい ID を作り直さない。

## 調査と情報の抽出

設計・実装前の調査にも下位モデルを使う。コードベース全体や複数 System の調査も可能とし、事前に対象ファイルを狭く限定することは必須にしない。
調査の目的と期待する報告を Task に書く。下位モデルは確認した事実と根拠のファイル・行番号、推測、未確定事項、調査範囲と未確認範囲を Report にまとめる。
Report は詳細資料への索引として使い、上位モデルは必要な原文だけに戻る。下位モデルの安い入出力を利用した情報整理で、上位モデルのコンテキストを抑える。
全体の使用量は下位モデルの読み取り・報告も含むため、重複調査を減らし、記録なしに節約効果を断定しない。

## 再開と既存変更

再開時は既存 Task／Report の工程・状態・決定・質問・変更ファイル・検証結果を読み、必要な箇所だけ再取得する。
現在の Git 状態と稼働中の担当も照合し、古い Report だけで完了や検証済みと判断しない。
ユーザーや別作業の変更を保持する。担当範囲外の変化は上位モデルへ報告し、自動で上書き・復元・整理しない。

## 実装フロー

### 1. 設計と対象範囲を整理する

上位モデルが設計資料と既存実装を必要な範囲で確認し、責務、所有、公開範囲、未確定事項、調査や編集の分担を整理する。
既存資料で決定済みのこと、現在の実装の事実、今回の提案を区別して Task に記載する。
広い調査は必要に応じて下位モデルへ委任し、Report を確認してから契約・実装方針を判断する。

### 2. ヘッダーと契約の草案を書く

下位モデルが Task と資料に沿って宣言と Doxygen を書く。
利用側に必要な操作の意味、引数・戻り値、単位、所有・有効期間、呼び出し前提、失敗時の挙動を記載する。
数値の上下限を一律に要求しない。値の意味から必要な制約を検討し、確定した範囲と境界での挙動を明記する。
検討していないものを「上限なし」などの保証として記載せず、Report の未確定事項にする。

### 3. 未確定事項を判断する

下位モデルは契約と担当範囲の中で判断できることを自律的に決める。判断できない事項だけ、質問・根拠・提案を Report にまとめて返す。
上位モデルは設計資料、ユーザーの意図、既存の慣習から判断できるものを判断し、Task に記録する。
上位モデルが判断できないものは、選択肢と影響を整理してユーザーに Q&A として提示する。
判断待ちの契約に依存する作業は進めず、独立した作業は続ける。
決定した契約をヘッダーに反映する。複数の API・System にまたがる決定は、文書更新の必要性も相談する。

### 4. 契約と検証方針をレビューする

上位モデルがヘッダーをレビューし、テストの期待値を決められる契約になっているか確認する。
変更内容とリスクに応じて、追加テスト、TDD、既存テスト、ビルド、統合・実行確認の必要性と範囲を決める。
単純な Getter などには追加テストを一律に要求しない。検証の未決定・実行・不要を区別し、不要と判断した場合は Task に理由を短く記載する。
依頼やリポジトリで必須とされている確認は、その指定に従う。

### 5. テスト・実装・必要な検証を行う

下位モデルが指定された工程を進める。
TDD を選んだ部分は、契約に対応するテストを先に書き、期待する振る舞いとの不一致による RED を確認してから実装する。
未定義シンボルのリンク失敗や環境エラーだけを、振る舞いの RED として扱わない。
テスト関連は利用可能な `cpp-automated-testing` と必要な `cpp-test-*` を使い、既存の基盤・検証コマンドを再利用する。
実装後は指定された検証を行う。成功した確認は、新しい変更・失敗・未解決の懸念がなければ再実行しない。
仕様の疑問や失敗は Report にまとめ、同じ状況で修正を繰り返さず上位モデルへ返す。

### 6. 完了をレビューする

上位モデルが対象の差分、契約との対応、必要な検証の結果、残る質問を確認する。
確認済み・未確認の範囲を区別してユーザーへ報告する。
Report の結果だけで問題なく判断できる場合は、長いログの再読や同じ検証の再実行を増やさない。

## 並列化

- 上位モデルが編集対象と依存関係を分けられる作業だけ、TaskId を分けて下位モデルへ並列委任する。調査のみの作業は、目的・観点を分担して重複を抑える。
- 編集範囲の重複確認は同じ run 内だけでなく、リポジトリ内の別 session／run の進行中 Task も対象とする。安全に分離できなければ直列に進める。
- 同じソース、共有ヘッダー、`.vcxproj` などを同時編集する担当は作らない。
- 同じクラスの `.h` と `.cpp` は、ヘッダーの契約確定を先にする。
- TDD 対象のテスト作成・RED 確認・実装は順序を保つ。
- 同じ出力先を使うビルド・テストは重複実行せず、統合後に必要な範囲を確認する。

## 機械処理

設定読み込み、TaskId 生成とテンプレートコピー、作業範囲と編集重複の検出、受け渡し内容の抽出、指定された検証の実行、結果と差分の集約は補助スクリプトへ移す。
契約の決定、質問へ回答できるか、検証の必要性、レビューの合否は上位モデルが判断する。

## 設定とテンプレート

モデル候補・固定値が未設定なら、今回のユーザー指定を使うか必要な設定を確認する。
テンプレートの正本は Skill の assets に置き、working 側の `_Template` へローカルコピーする。
既存の作業ファイルをテンプレートで上書きしない。
